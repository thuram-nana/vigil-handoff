**BRING-UP GOTCHAS (all hit + fixed, all reusable):**
1. **`vigil target up` IS WRONG — the launcher is `target up`** (a SEPARATE console-script at `~/vigil/.venv-offense/bin/target`, installed by bootstrap `install_launcher target`). `vigil` has NO `target` subcommand → "invalid choice: 'target'". My `tools/vps-bringup.sh` used `vigil target up || true`, and the `|| true` SILENTLY swallowed the error, so MERIDIAN never started on the first bring-up. **FIX vps-bringup.sh: `vigil target up` → `target up` (still owed in the repo).** `target down` works (prints "stopped range (pid …)").
2. **`vigil` + `target` NOT on PATH after bootstrap.** They live in `.venv-offense/bin/`. The bring-up's `vigil services up` died with "vigil: command not found". Fix: add `.venv-offense/bin` to PATH + persist in `~/.bashrc`. A non-interactive `ssh host 'cmd'` does NOT source ~/.bashrc, so one-shots must use the full path `~/vigil/.venv-offense/bin/{vigil,target}`.
3. **Egress gateway fail-closes without a scope source** → container exits(1): `RuntimeError: no gateway scope source — set VIGIL_GATEWAY_SCOPE_HOSTS … or VIGIL_GATEWAY_CHARTER_SLUG`. Fix: `export VIGIL_GATEWAY_SCOPE_HOSTS=api.anthropic.com` (persist in ~/.bashrc) before `vigil services up`. (The `vigil-gateway-firewall` sidecar legitimately Exits after installing nftables; only `vigil-gateway` must stay Up.) See [[vigil-oob-subsystem-and-authority-gate]].
4. **`vigil up` aborts "the sovereign cockpit did not start / print a token"** once the spine has records: the cockpit "refusing to run `serve` — the spine is in the LEGACY single-file layout (pre-segment)". The FIRST `vigil up` works (empty spine); then sealing keys WRITES the first signed records in the legacy format; on restart the cockpit refuses. **FIX: `vigil upgrade`** (migrates legacy→segmented, backs up to ~/.sigil/backups, rollback `sigil restore`), then `vigil up`. (Same blocker noted in [[vigil-meridian-range-program]] Act 4.)
5. The cockpit **persists its bearer token to disk**, so a `vigil up` restart keeps the SAME `?token=…` sign-in URL (it does NOT always rotate).

**AUTONOMOUS-SUITE 40-min-HANG FIX (DONE, commit 3d39f628 on `meridian-s5-expansion`, pushed + VPS-deployed + live-verified 5s):** the gated executor's PER-ENGAGEMENT `--request-budget` is a SOFT refusal `{"status":0,"refused":"…request budget N exhausted"}` (NOT an exception; `http_executor.gated_fetch`), SEPARATE from the AuditEngine's own `max_requests`. Pre-fix the sweep never noticed it → kept probing every crawl-expanded surface, and each blind OOB check (`except Exception: pass`) still paid its full 2.0s `poll_deadline` → ~9000 budget-exhausted events, never finalized, 0 facts, 40+ min. Fix in `scanner/engine.py`: `_counted_send` detects the soft refusal via `_is_request_budget_refusal()` + a sticky `self._budget_exhausted`, and `BudgetExceeded` is now a **`BaseException`** (control-flow, like KeyboardInterrupt) so the OOB `except Exception` CANNOT swallow it; every legit sweep-end catches it explicitly. 5-case offline regression `scanner/tests/test_engine_budget_terminal.py` (no wall-clock; run via pytest or a `pytest.raises` shim — pytest is NOT in `.venv-offense`). Lesson: a budget enforced by the GATE layer as a soft-refusal dict must be detected at the engine's send seam AND raised as a BaseException, or broad `except Exception` handlers downstream silently swallow the stop.

**WIREGUARD GOTCHAS (all hit; load-bearing):**
1. **The VPS runs `ufw` with `-P INPUT DROP`** (only SSH + established allowed). WG needs TWO rules or it silently fails: **`sudo ufw allow 51820/udp`** (else the handshake packets arrive — confirmed via `sudo tcpdump -ni any udp port 51820` — but are DROPPED, so `wg show` shows `0 B received, N KiB sent`, no handshake) AND **`sudo ufw allow in on wg0`** (else the handshake completes + `ping 10.8.0.1` works but every TCP to the forwarder ports on `wg0` is dropped → `curl 10.8.0.1:8770` = 000). Both persist (ufw enabled).
2. **NEVER trust a non-root `nft list ruleset`** — as `vigil` it returns empty (perms), which I misread as "no firewall / permissive." Check `sudo ufw status` / `sudo iptables -S INPUT` (shows the DROP policy) / `sudo nft list ruleset`.
3. **`vigil down` only stops TRACKED pids** (`.vigil-live/ui/pids`). A hand-started `vigil up` (nohup/detached) is UNTRACKED → `vigil down` reports "stopped 0", the old instance keeps squatting :8770/:8733/:8787/:8799, and `systemctl start vigil-autostart` then can't bind → unit stuck `activating (auto-restart)`, `ExecStart status=2 "port already in use"`, while the 200s you see come from the OLD squatter. Fix: free the loopback ports — `fuser -k 8770/tcp 8733/tcp 8787/tcp 8799/tcp 19010/tcp 19011/tcp` as the vigil user (kills vigil-owned squatters; the ROOT-owned WG-forwarder socats on 10.8.0.1 survive the permission check) — then the enabled systemd units bind on their next Restart cycle.
4. **`pgrep -f "vigil up"` / `pkill -f "bin/vigil up"` SELF-MATCH the ssh command line** (its argv contains the pattern) → false "already running" and you can kill your own shell. Use `fuser -k <port>` or a pattern that isn't in your own command.
5. **Detaching `vigil up` over ssh**: `setsid bash launcher.sh >/tmp/log 2>&1 </dev/null & disown; exit` with NO trailing commands in that ssh — a trailing `sleep/curl` keeps the ssh channel open (children inherit the pipe) so the ssh hangs till timeout (looks like a failure; vigil up actually started). Verify in a SEPARATE ssh.

**REMOTE-ACCESS AUTH GOTCHA + FIX (2026-10-22, deployed+verified).** Symptom: over WireGuard the UI looked logged-in-but-DEAD — the offense chip showed "Offense up" yet was NOT clickable, and (really) EVERY API call 401'd (incognito didn't help). ROOT CAUSE: the proxy now binds the WG IP DIRECTLY (`10.8.0.1:8770`, no VPS-side loopback forwarder), so it SCRUBS the owner token from the served HTML for the non-loopback peer → `<body data-token="">` (the `__VIGIL_TOKEN__` placeholder rewritten to EMPTY). The scrub keys on the TCP PEER being loopback, NOT the Host header (a raw socat forward keeps `Host: 127.0.0.1` but the peer is `10.8.0.2`), so even a loopback-Host request via the chain gets scrubbed. The UI read its token ONLY from `data-token` (app.js `boot()`: `if (ds.token && ds.token!=="__VIGIL_TOKEN__") CFG.token=ds.token`) with NO `?token=` capture and no cookie → empty `X-SIGIL-Token` everywhere → 401 → `canStart=false` → the non-clickable "Offense up" (up=true comes from the lenient `probeOffenseConsole` fallback treating any non-5xx as up). The chip toggle itself (commit cd5b6526) was fine; the token never reached the page. FIX (deployed to `.vigil-live/ui/app.js` + `packages/vigil-ui/app.js` + branch `aegis-multigateway-blocking`): app.js `boot()` now ADOPTS `?token=` from the bookmark URL into sessionStorage (then `history.replaceState` strips it from the address bar), the SAME pattern as the OIDC bearer, guarded by `if (!V.token())` so an embedded data-token (owner/loopback) or an active per-user login still wins. So the `?token=` bookmark authenticates regardless of the proxy's loopback-scrub. `app.js` is served `no-cache`+ETag so a plain F5 picks up the new file (no hard-refresh needed). Zero-deploy workaround (if ever needed again): DevTools console `sessionStorage.setItem('vigil.session.token','<tok>'); location.reload()`. Alternative permanent restore = proxy back on `127.0.0.1` + a VPS-side `socat 10.8.0.1:8770→127.0.0.1:8770` (the old working topology, where the proxy sees a loopback peer and embeds the token).
