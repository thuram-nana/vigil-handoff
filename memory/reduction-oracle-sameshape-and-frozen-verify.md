Both lessons came from red-penning the `graphql_batching` governed-engage FACT slice (meridian-s5, Oct 2026). See [[fake-fixture-pattern]], [[measured-claim-discipline]], [[anti-hallucination]].

**L1 — a capture-bound reduction refactor can silently DROP soundness bindings, and a "same-shape negative control" must exercise the ADVERSARIAL same-shape.**
`GraphQLBatchingCheck.assess` was refactored to the F7 capture-bound form `from_predicate({response_body, batch_result_count=reduction, sent_batch}, {gt:[count,1]} + contains["data"])`. The refactor DROPPED the two bindings the prior form had: the `_is_graphql_shaped` gate AND `eq[returned_len, sent_batch]`. The reduction counted ANY top-level array element with a non-null `data` member, so a benign >=2-element data array — a static JSON file, a REST/collection feed, a dashboard list — minted a signed FACT that re-verified offline. The LLM supplies `claimed_class`+URL, so it could point it at any in-scope static-array endpoint. The slice's own "DECISIVE same-shape negative control" only exercised the **count-0** case (a single object / errors-only body) — the TRIVIAL negative — never a benign >=2-element array, which is exactly where `gt[count,1]` is unsound. **RULE: a same-shape negative control must be the benign input that most RESEMBLES the vuln's signature (here: a >=2-element data array that never executed VIGIL's ops), not the trivial absence. count-0 ≠ same-shape.** Fix = bind to VIGIL's OWN distinct per-op aliases: `build()` sends `{ v{i}: __typename }`, the reduction counts positions `i` whose `data` echoes `v{i}`, predicate `gt[sent_batch,1] + eq[batch_result_count, sent_batch]`. A static list / REST feed can't carry VIGIL's `v{i}` aliases → count 0. Residual (NAMED, not benign/model-reachable, impact-nil, same class as [[weaponized-arm-corpus-provenance-triplelock]]/access_control compromised-deployment): the `v{i}` scheme is PREDICTABLE, so a deliberately-deceptive in-scope target could hand-echo it; a per-probe HIGH-ENTROPY alias (like the CORS/smuggling canaries) would retire it (follow-on, feasible per L2).

**L2 — offline FACT re-verification uses the FROZEN signed reduction value + signature tamper-evidence, NOT a re-run of the reduction.** There is no reduction registry on the verify side. At LIVE mint, `assess` computes the reduction (`batch_result_count`) over the captured bytes, stores it in `observed_evidence`, and the signature binds the WHOLE `observed_evidence`. Offline `verify_certificate` re-evaluates the PREDICATE (`eq[count, sent_batch]`) over that frozen count; tampering the retained `response_body` to a benign array still FAILS verify because the signature binds it (even though the predicate no longer references `response_body`). So "re-verifies offline" = predicate-over-signed-reduction + tamper-evidence, **NOT** re-reduction-from-bytes. Same pattern as `graphql_introspection.schema_returned`'s `introspection_type_count`. **IMPLICATION: a reduction MAY use per-probe live state (e.g. a high-entropy nonce) because the value is frozen at mint — but do NOT overclaim the cert as "re-derives the reduction from bytes."** The `provenance_refs={"...":"reduction"}` tag marks live-mint byte-binding, not verify-side recomputation.
