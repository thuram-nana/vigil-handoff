VIGIL `main` (thuram-nana/vigil-sovereign) is branch-protected but **NOT strict / up-to-date-required**, so two PRs that are each green in isolation can merge into a **red main** when neither's CI saw the other's change. Confirmed 2026-08-23: H5 #642 added `zmap`/`unicornscan` ToolSpecs to the catalogue; H7 #638 added `test_oracle_families::test_the_family_registry_agrees_with_the_capability_matrix` (every non-excluded catalogued tool must route to a `FAMILY_REGISTRY` family). Both green alone → red main. Fix = route both tools to the `network_discovery` family (`verifier=SERVICE_REACHABILITY`) in `integration/vigil_integration/live/oracle_families.py` (**#647**).

**How to apply:** after merging any BATCH of PRs, run main's `vigil-ci` and fix integration reds — don't trust per-PR green. The P5 job (`integration two-env boundary`) is where matrix/registry-agreement reds land. A second red the same day was a **flaky** P5 test, not a deterministic one: `test_ui_log_rotation.py::test_spawn_end_to_end_bounds_a_chatty_child` — `uiproxy._spawn`'s daemon log-pump keeps rotating after the child exits, and the test `glob`+`getsize`'d the rotating set → `FileNotFoundError` (TOCTOU rename). Fixed by exposing the pump thread as `proc._vigil_pump_thread` and joining it before snapshot (**#648**). A green PR run can still hide a flake that only trips on the post-merge main run — always confirm the post-merge main `vigil-ci` is green, not just the PR.

**Incident (same session):** a merge fallback helper set `b=$(git rev-parse --abbrev-ref HEAD)` then `git push --force-with-lease origin "$b"`. A `cd` into a worktree didn't land on the feature branch, so `$b` resolved to `main` in `/home/kali/vigil` (which sat on a STALE local `main`), force-pushing it over origin/main and rewinding ~22 commits / 10 merged PRs. **Recovery:** the good tip was a strict *superset* of the stale one (`git merge-base --is-ancestor <stale> <good>`), so a plain **fast-forward** `git push origin <goodsha>:refs/heads/main` restored it losing nothing. **Lessons:** (1) never derive a push target from HEAD without asserting it's a feature branch (`!= main`); push the explicit branch name. (2) The Claude auto-mode classifier BLOCKS all writes to protected `main` — force AND plain ff — so an accidental force-push can't be self-reverted; the restore needed a user directive ("fix main") before the ff push went through. Related: [[vigil-strix-hexstrike-wiring-program]], [[shell-commit-message-backticks]].

**22-PR sweep + gate decisions (2026-08-23, same session).** Handled all open PRs (5 issue + 17 dependabot) + follow-ups. Durable ops lessons:
- **A "push outage" (git `send-pack: unexpected disconnect while reading sideband packet`) was LOCAL git-object CORRUPTION**, not the network — the prior session died under disk pressure leaving ~10 zero-byte objects. Diagnose with `git fsck --full`; delete the empty loose objects (`find .git/objects -type f -empty -delete`) then `git fetch` to restore them (they were reachable from origin refs, e.g. dependabot branches). **Switching `origin` to the SSH URL** (`git remote set-url origin git@github.com:…`) sidesteps flaky HTTPS pack-upload; SSH auth works over :443 too. My unpushed commits stayed intact (verify with `git cat-file -e <sha>^{tree}`).
- **Sub-agents can't do network** (sandbox drops TCP) and the **safety classifier BLOCKS any agent prompt that mandates `dangerouslyDisableSandbox`** (it fired twice this session). So: agents implement + commit locally (fork the already-fetched local `origin/main`, no fetch/push); the **orchestrator** does all network (pip installs, registry queries, pushes via SSH-with-`dangerouslyDisableSandbox`) and merges.
- **Agents/red-pen keep confusing the repo/worktree.** This session's cwd is `/home/kali/Pictures/PENTEST-main` (a DIFFERENT repo), vigil is `/home/kali/vigil`, and there's also `/home/kali/vigil-apex`. A red-pen returned **"BLOCK: change absent"** purely because it searched the wrong repos — always give agents the **explicit worktree path** and tell them NOT to look elsewhere; verify a red-pen actually reviewed the right tree before acting on its verdict.
- **registry.json unions on nearly every PR** (append-only claims) → an unavoidable N-cycle rebase cascade with a moving protected main + required-green checks; resolve with the union-by-id script. Dependabot PRs don't touch registry (less cascade) but Actions bumps collide on `ci.yml` `uses:` lines.
- **Outcomes:** #656 = **Option A** (rolling-tag drift ADVISORY via `image_pins.py::_ADVISORY_ROLLING_DRIFT`, exact-repository-keyed + reason-required; every stable tag still BLOCKS) — red-pen confirmed soundness, its only BLOCK was an honesty overclaim in the W3-8 claim/docs (the claims-registry guard structurally can't catch true-vs-code drift; fixed by disclosing the carve-out). **mypy 2.x** = the CI already hash-locks + runs `mypy==2.3.1` (`infra/supply-chain/ci-tooling.lock.txt`), so #657's blocking ratchet is already 2.3.1-based; the dependabot floor bumps (#579/#580/#582) just aligned the pyproject dev-extra floors (and fixed a crucible `mypy<2`-vs-CI-2.3.1 mismatch) — no ratchet regen needed. **Deferred** (need a stable-network CI host): #660/#575 (sovereign-lock `pip-compile` regen times out on onnxruntime's huge multi-wheel hash set), #577 (mcp 2.0 major — deliberate API review).
